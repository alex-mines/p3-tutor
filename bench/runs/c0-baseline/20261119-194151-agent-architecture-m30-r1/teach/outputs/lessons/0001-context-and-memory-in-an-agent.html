One more thing to hold on to from your first lesson: a language model knows only what it learned in training plus the text it is given. Everything below is about managing that given text.

The context window 6 min

Start with a concrete case. A student types: "Can I use the laser cutter for acrylic?" Before the model writes a word, the program assembles a block of text for it to read: the assistant's instructions, the list of tool descriptions, and the student's message. The model reads all of it, then writes its reply.

That block is the context: all the text the model can see on one call. The context window is the limit on how much text fits in it. Size is counted in tokens, the small chunks of text (often a short word or a piece of a longer one) that models read and write. Both what goes in and what comes out count against the window (Claude docs: context windows).

Three facts follow, and they matter for your design.

  1. Nothing outside the window exists for the model. If a fact is not in the context on this call, the model cannot use it. It cannot "go and look" except by requesting a tool.
  2. Bigger is not automatically better. Anthropic's engineers describe context rot: as the number of tokens grows, the model's ability to recall details from that context tends to decrease. Their advice is to find the smallest set of high-signal tokens that makes the right outcome likely (Effective context engineering for AI agents).
  3. Tokens cost money. You pay for the tokens you send in and the tokens that come out. The next section shows why this multiplies in a loop.
Window sizes keep changing. Current Claude models list windows of 200K tokens up to 1M tokens, and requests above 200K tokens are billed at a higher rate on some models. Check the live docs when you choose a model, not this page.
A common mix-up

"A model with a huge window can just hold all our manuals, so we do not need to design anything." It is tempting because the window sounds like storage. But every token you load is paid for on every call, and a crowded window makes details harder for the model to recall. The window is a workspace, not a filing cabinet.

What is kept between steps 6 min

Now the loop you already know. The model is called, asks for a tool, the program runs it, and the model is called again. Here is the key fact: the model keeps nothing between calls. Each call starts blank. What looks like the model "remembering" the earlier steps is the program re-sending them. The history in the context (the student's question, each tool request and each tool result) is the agent's short-term memory, and the program owns it.

Take the request "Is the laser cutter free tomorrow at 3 pm, and do I need training?" The loop makes three tool calls and then answers. Here is what the context holds at each model call. The sizes are made up to show the pattern, not measured:

The final context is only 7,730 tokens, but you are billed 21,820, because every call re-reads everything before it. The earlier the big tool result lands, the more times you pay for it. Here the 4,000-token manual search is re-read on call 4 as well as call 3. This is the budget lever your mission cares about: cost per request grows faster than the number of steps.

When a window fills up, or when old results are no longer needed, the program has choices. Anthropic describes keeping the context tight: clearing old tool results that have already been used, or summarising a long history into a short note and continuing from the summary (Anthropic: context management). Whatever is cleared is gone from the model's view, so only clear what the next step does not need.

A common mix-up

"The model remembers what it did in step 1 because it did it." It does not; the program re-sends step 1. If your program forgets to append a tool result to the history, the model will behave as if the tool never ran, and may call it again, which is how loops go round in circles.

What is kept between sessions: notes 6 min

A session here means one conversation: a student opens the assistant, talks, and leaves. When the next student, or the same one next week, starts a new session, the context starts empty again. The window is gone. So anything that must survive has to be written somewhere outside the window, and read back in when needed.

Take Maya, who finished laser cutter training on Tuesday. On Friday she asks to book it. The assistant has no idea who she is. Unless something was saved, she must prove her training all over again.

The simplest fix is notes as memory: the agent (or your program) writes short facts to a file or database, and on the next session loads the relevant ones into the context. Anthropic's memory tool works this way: Claude creates, reads, updates and deletes files in a memory directory that you store, and it checks that directory at the start of a task (Claude docs: memory tool). The data lives on your side, so you control what is stored.

Good memory design asks three questions about every fact:

  • Must it survive the session? Maya's training status, yes. The student's phrasing of a question, no.
  • Is the saved version trustworthy? A note can go stale. If a training certificate expires, the note "Maya: laser OK" is now wrong. Store a date, or better, store a pointer to the real record and look it up.
  • How much comes back in? Loading every note into every session grows the context for nothing. Load what this student and request need.
A common mix-up

"The assistant remembers Maya because it is the same assistant." It is the same program and model, but not the same context. Without something written down and loaded back, a new session knows nothing about the last one.

Retrieval: finding the right page 7 min

Your manuals are far too long to put in the context on every call (Section 2 showed what that costs). So the assistant needs to find just the right page. That is retrieval: searching an outside collection and putting only the best matches into the context.

Concrete case: "What speed should I cut 3 mm acrylic at?" The assistant should not read the 200-page laser manual. It should fetch the one table that answers it.

The usual recipe, often called retrieval-augmented generation (RAG), has two stages (Anthropic: contextual retrieval):

  1. Prepare ahead of time. Split each manual into chunks (a section or a few paragraphs). Index them so they can be searched, for example by keywords or by embeddings, which are lists of numbers that place chunks with similar meaning close together.
  2. At question time. Search with the student's question, take the top few chunks, and place them in the context. The model answers from those chunks.

In an agent, retrieval is simply another tool, for example search_manuals(query), that returns a few chunks. The model decides when to call it. Anthropic calls this "just-in-time" retrieval: the agent holds light references and loads data into context only when it needs it, instead of preloading everything (context engineering).

Retrieval can fail, and that is where the design work is. If the answering table is split from its heading ("Acrylic, 3 mm") the chunk may say only "Speed: 20, Power: 60" and the search cannot tell which material it is. Anthropic's fix, contextual retrieval, adds a short explanation of where each chunk comes from before indexing it. They report this cut failed retrievals by 35% with embeddings alone, and by 49% when combined with keyword search (same source). Those are their results on their test data, so treat them as a sign of what is possible, not a promise for your manuals.

A common mix-up

"Retrieval is the same as the model knowing the manual." Retrieval hands the model a few chunks. If the search returns the wrong chunk, the model answers from the wrong page, and may sound just as sure. Always judge the search separately from the answer.

Worked example and practice 5 min

Worked example

Place each item: window, note, or retrieval. The item is "the laser cutter's recommended speed for 6 mm plywood".

  1. Does it exist anywhere else? Yes, in the laser manual. So it is not a note; notes are for facts that exist nowhere else.
  2. Is it small enough to load on every call? No. It is one row of a long manual, and every other machine has similar rows. Loading all of them each call is expensive.
  3. Decision: retrieval. The assistant calls search_manuals when asked. The returned row lands in the window for that request only.

Summary 2 min

  • The context window is everything the model sees on one call. The model keeps nothing between calls; the program re-sends the history.
  • Because each call re-reads the whole history, cost grows faster than the number of steps. Keep tool results small.
  • Between sessions the window is empty. Anything that must survive goes in notes, written out and loaded back.
  • Long documents belong in a searchable collection. Retrieval puts only the best few chunks into the window.
