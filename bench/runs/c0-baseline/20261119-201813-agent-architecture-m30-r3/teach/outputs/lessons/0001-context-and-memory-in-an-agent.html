Context and memory in an agent

By the end of this lesson you can decide, for the makerspace assistant, what stays in the model's context during a request, what gets saved between a student's visits, and what is looked up in the manuals only when needed.

Objective O3: context and memory in an agent About 30 minutes Builds on the agent loop (learning record 0002)
Why this matters for you

Your assistant must answer from long machine manuals and remember each student's training status between visits, all on a small model budget. Those are three separate design decisions: what goes in context, what goes in saved notes, and what gets retrieved. You will defend them at your design review.

Warm-up 2 min

Recall

From the agent-loop session: a student asks, "Is the laser cutter free tomorrow?" In your own words, what happens between the question and the final answer? Who runs the calendar lookup, the model or the program around it?

Check your answer

The program calls the model; the model replies with a request to use a tool such as check_calendar, with arguments. The program runs the tool, adds the result to the conversation, and calls the model again. This repeats until the model writes a final answer or a limit stops the loop.

Today's question is what the model can see each time it is called again. That is the context.

The context window: all the model sees 6 min

Start with a concrete case. A student types: "How thick can the material be on the laser cutter?" Your program calls the model. What does it send?

Not just the question. It sends a bundle of text:

  • the system prompt: your instructions ("You are the makerspace assistant. Be brief. Never book a machine without checking training.");
  • the tool descriptions: the names and descriptions of check_calendar, search_manuals and the rest;
  • the conversation so far: the student's messages, the model's earlier replies, and any tool requests and results.

All of that, together, is the context: the text the model is given on one call. The context window is the limit on how much text the model can take in on a single call, counting the text it writes back too. The model works in tokens, which are small pieces of text, often a short word or part of a longer one. Limits and prices are both counted in tokens. Anthropic's documentation describes the window as the model's working memory for a conversation, and lists current window sizes per model, so check the context windows page rather than trusting a number from a lesson.

Here is the idea that changes how you design: the model has no other view of the world. It cannot open the booking system, remember last week, or glance at a manual. If a fact is not in the context on this call, the model does not have it. You can feed it facts only by putting text there.

A common mix-up

"The assistant remembers earlier conversations by itself." It is tempting because chatbots feel like they know you. But the model only reads what is in the current context. A chat app seems to remember because its program sends the earlier messages again with each new one. If your program does not do that, or does not save them for next week, the model starts blank.

Between steps: the transcript grows 7 min

Now connect this to the agent loop. Each step of the loop is a separate model call, and the model does not carry anything over from one call to the next. What carries over is the transcript: the running list of messages, tool requests and tool results that your program keeps and sends again each time. Your program owns it. The model rereads it from the top on every call.

That has a direct cost consequence. Anthropic's engineering team frames context as a limited resource: the goal is the smallest set of high-signal tokens that makes the result you want likely (Effective context engineering for AI agents). They also describe context rot: as the amount of text grows, the model's ability to recall details from it tends to get worse. So a long transcript is not just pricier, it can be less reliable.

Worked example: one request, four calls

A student asks: "Is the laser cutter free tomorrow at 3 pm, and do I need training?" Assume, for illustration, that the system prompt, tool descriptions and question take 2,000 tokens. The model makes three tool requests and then answers. The tool results are:

  1. Call 1 reads the 2,000-token base. The model requests check_calendar. Result: 300 tokens.
  2. Call 2 reads 2,000 + 300 = 2,300 tokens. The model requests search_manuals. Result: a manual page, 1,500 tokens.
  3. Call 3 reads 2,300 + 1,500 = 3,800 tokens. The model requests check_training_record. Result: 200 tokens.
  4. Call 4 reads 3,800 + 200 = 4,000 tokens and writes the answer.

The final context is 4,000 tokens, but the model was charged for reading 2,000 + 2,300 + 3,800 + 4,000 = 12,100 input tokens. (I ignored the small tokens the model writes for its requests.) The early parts of the transcript are paid for again on every step.

Three levers follow, and you can use them in your design:

  • Keep tool results small. A tool that returns a whole manual chapter when one paragraph would do is paid for on every later call. Anthropic recommends tools that return token-efficient output (same article).
  • Clear what is no longer needed. Once the model has used a result, an old result can be dropped or shortened. Anthropic's platform offers "context editing" for this, and reports that it improved performance on its tests on its own and more when combined with a memory tool (Managing context).
  • Cap the loop. The step limit from the agent-loop session also limits how large the transcript can get.
A common mix-up

"A bigger window fixes everything." A bigger window lets more fit, but you still pay for every token read on every call, and a very long context can be less reliable. For a small budget, the aim is a small, relevant context, not a full one.

Check yourself

In the worked example, you shrink the manual page from 1,500 tokens to 500. What happens to the total input tokens charged for the request?

Show the answer

The third option. The page appears in the context of call 3 and call 4. Saving 1,000 tokens in each of those two calls gives a saving of 2,000: 12,100 − 2,000 = 10,100.

Between sessions: nothing, unless you save it 6 min

When a request ends and your program stops sending the transcript, the context is gone. Next week, when the same student returns, the model starts with only the system prompt and tool descriptions. It has no idea they finished laser training on Tuesday.

So memory, for an agent, is not something inside the model. It is information your program saves outside the context and later puts back into it. Two kinds of saving matter:

KindWhat it isMakerspace example
Short-termThe transcript of the current request or conversation, resent each callThe calendar result the model just got for the laser cutter
Long-termNotes saved to a file or database, and loaded into a later session"Sam: laser cutter training done, 12 Oct"

The simplest long-term memory is notes: short text the assistant writes down, in a file or database, and reads later. Anthropic's memory tool works exactly this way: Claude can store and retrieve information across conversations in a directory of memory files, and your own application code carries out the file operations, because Claude only requests them (memory tool documentation). That matches what you learned about the loop: the model asks, the program acts. The documentation also says your handler must reject paths outside the memory directory, a reminder that you own the safety of whatever the model asks to write.

You do not need that specific tool to build this. In Python you could save a small JSON file per student. The design decision is what to save and when to load it:

  • Save facts that are costly to rediscover and stay true: training completed, and the date.
  • Do not save everything. A full transcript of each chat would fill the context next time, and most of it will never matter.
  • Load only what this request needs. At the start of a session, load the student's record. Do not load every student's.
Where the "truth" lives matters. For training status, the official record, in your tool check_training_record, should win over any note the assistant wrote itself. Notes can be stale. A note is a hint to check, unless you are sure it is current.

Retrieval: finding the right page 6 min

The manuals are the third piece. A machine manual may run to hundreds of pages. You cannot put all of it in every context: it may not fit, and if it did you would pay to reread it on every call. Instead, the program looks up the relevant parts when a question arrives.

Retrieval means searching a store of text for the pieces most relevant to the current question, and putting only those into the context. The common pattern is called retrieval-augmented generation, or RAG. In outline:

  1. Prepare once, ahead of time. Split each manual into chunks, short passages of a few paragraphs, and index them so they can be searched.
  2. At question time, search. Turn the question into a search over the chunks and take the top few matches.
  3. Put the matches in the context, usually as the result of a search_manuals tool call, and let the model answer from them.

That is the search_manuals tool you already have in your design. Retrieval is not a new mechanism: it is a tool whose result is a few relevant chunks.

Two search styles are common, and they fail in different ways. Keyword search (such as the BM25 method) matches the exact words, so it finds "kerf" if the student typed "kerf", but misses "cut width". Embedding search compares meaning, so it can match "cut width" to "kerf", but it can miss exact part numbers or error codes. Anthropic reports that combining the two, and adding a reranking step that reorders the top results, cut retrieval failures substantially in its tests (Contextual Retrieval). In the same post, they add a short explanation of where each chunk comes from before indexing, because a chunk like "Set it to 40%" means nothing without knowing which machine and which material it is about.

A common mix-up

"Retrieval means the model learned the manual." Nothing is learned or changed in the model. Retrieval only places text in the context for this call. If the search returns the wrong chunk, the model answers from the wrong chunk, or says it cannot find the answer. That is why a good chunk, with its machine name attached, matters.

One more design choice, from Anthropic's context-engineering article: you can retrieve just in time, loading a source only when the model asks for it, rather than loading a lot up front. For the makerspace assistant, that means a search_manuals tool the model calls when it needs a page, not a system prompt stuffed with manuals. The same article suggests the agent keep light references such as file names and fetch the content when needed.

Worked example and practice 6 min

Worked example: a returning student

Jordan returns to the makerspace and asks: "Book me the vinyl cutter on Thursday afternoon and tell me what blade setting to use." Decide what goes where.

  1. System prompt and tool descriptions go in context every call. They define the assistant and its tools. Keep them short, because they are reread on every call.
  2. Jordan's saved note is loaded at the start. It says "vinyl cutter training done." That one line is cheap and answers the question "may Jordan book this?" (verified with check_training_record before booking, because notes can be stale).
  3. The blade setting is retrieved, not saved. The model calls search_manuals("vinyl cutter blade setting") and gets two chunks back, perhaps 600 tokens. It does not need the whole manual.
  4. The calendar result stays in the transcript for this request only. After the booking is made, the slot is in the booking system, which is the source of truth, so no note is needed.
  5. At the end, one new note may be saved: "Jordan prefers afternoons." Only if the team decides that is worth keeping. Everything else, including the blade chunks, is discarded with the context.

Show a solution

(b) Priya's induction date is a fact about one student that changes rarely. It can be a saved note for fast loading, but the authoritative answer lives in the training record tool, so check that before relying on it. (c) "Always confirm before booking" is a rule for every request, short, and fixed: it belongs in the system prompt.

Cost check: the system prompt is reread on every call, so keep it for rules that apply to almost every request. Details that apply only sometimes, like material limits, should be retrieved.

Summary 2 min

  • The model sees only its context on each call: system prompt, tools and the transcript. Nothing else exists for it.
  • Each loop step is a new call that rereads the whole transcript, so cost grows with the sum over steps; keep tool results small.
  • Memory is not inside the model: the program saves notes outside the context and loads the right ones back in.
  • Retrieval is a tool that searches chunks of long text and puts only the best few into the context.
