Context and memory in an agent

By the end of this lesson you can decide, for each piece of information in the makerspace assistant, whether it belongs in the context, in saved notes or data, or in a searchable manual, and say why.

Objective O3: context and memory in an agent About 30 minutes Builds on the agent loop (learning record 0002)
Why this matters for you

Your assistant has to answer from long machine manuals and remember each student's training status between visits. Both are memory decisions, and you will have to defend them at your design review. They also drive cost, because you pay for the text the model reads on every step.

The context window 6 min

Start with an everyday case. You phone a friend who has no notes and a very short memory for the call. To get help with your homework you have to read the whole problem aloud, and if the call drops, you start again from nothing. A language model is like that friend.

Each time the program calls the model, it sends one block of text, and the model answers from that block alone. That block is the context: everything the model can see for that call. It holds the system prompt (the standing instructions), the tool descriptions, the conversation so far, and any tool results. The model has no other source. It does not look anything up on its own and it does not carry anything over from the previous call.

The context is measured in tokens, the small chunks of text a model reads and writes; a token is roughly a short word or a piece of a longer one. The context window is the limit on how many tokens one call can hold, counting both what you send and what the model writes. Past the limit, the call fails or something has to be dropped.

Anthropic's engineers define context engineering as curating and maintaining the best set of tokens available to the model at each call, which is wider than writing a good prompt (Effective context engineering for AI agents).

Why size matters for cost and quality

Two things follow, and both bear on your budget. First, you pay for the tokens the model reads, and on every call it reads the whole context again, so a long context makes every call dearer. Second, more is not always better. Anthropic describes context rot: as the number of tokens in the window grows, the model's ability to recall information from it accurately drops. Their goal is the smallest set of high-signal tokens that still gets the result (same post).

So the window is a small desk, not a warehouse. You choose what goes on the desk for each call.

A common mix-up

"A bigger context window means I can drop the whole manual in and be done." It is tempting because the window limit is the first number people hear. But a window that fits the manual does not make it free or reliable: you pay to send it on every call, and recall gets worse as the context fills. Choosing what goes in still matters.

What is kept between steps 6 min

In your agent loop, every step is a separate model call, so the same rule applies inside a single request. The program keeps a list of everything so far and sends the whole list at each step. After each tool runs, the program adds the model's request and the tool's result to the list. This list is often called the message history.

Worked example: counting what you pay for

Suppose the fixed part (system prompt and tool descriptions) is 1,000 tokens, the question is 50 tokens, and each tool result adds 500 tokens. The numbers are made up, to show the shape.

  1. Call 1 reads 1,000 + 50 = 1,050 tokens.
  2. Call 2 reads the above plus the first result: 1,550.
  3. Call 3 reads 2,050, and call 4 reads 2,550.
  4. Total read across the request: 1,050 + 1,550 + 2,050 + 2,550 = 7,200 tokens, although the new information was only about 1,550 tokens.

Most of the cost is the same text read again. If the manual excerpt were 5,000 tokens instead of 500, every later call would carry it too.

This is why careful agent builders keep tool results short and tidy, and clear out results they no longer need. Anthropic reports a context-editing feature that clears stale tool calls and results from inside the window as it nears its limit, and says that combining it with a memory tool improved performance by 39% over a baseline in their test (Managing context on the Claude Developer Platform). Treat the number as one company's test, not a promise for your assistant. The idea is what to take away: old results are the first thing to trim.

A second tool is compaction: when the history gets long, ask the model to write a short summary of it and continue from the summary. Detail is lost, so it suits long tasks more than a short booking chat.

What is kept between sessions 7 min

A session is one conversation, from the first message to the last. When it ends, the program throws the message history away unless you save it. A new session starts with an empty context. So what happens to a student who was told last week, "You still need to finish the laser cutter safety module"?

A common mix-up

"The assistant will remember the student next time." It is tempting because chat products often seem to. But the model itself keeps nothing between calls, and your program keeps nothing between sessions unless you write code to save and reload it. Memory is something you build.

Memory across sessions is information saved outside the model, then loaded into a later context when it is needed. There are two forms, and they suit different jobs.

FormWhat it isMakerspace example
Structured recordA database row or file your program owns, read through a toolStudent 4471: laser cutter safety module passed on 3 March
NotesShort free-text files the agent writes and reads, in a folder your program controls"Prefers evening slots. Often asks about 3D printer filament types."

Anthropic's memory tool is an example of the second form. It lets the model store and retrieve information across conversations in a directory of memory files. It runs on the client side: the model only asks for a memory action, and your application carries it out against storage you control (Memory tool documentation). That fits what you already know about the loop: reading and writing notes is just another tool call that your program runs.

Which form for which fact

Training status is a fact that must be exactly right: it decides whether someone may use a saw. Keep it in a structured record, and have the booking tool check it, rather than trusting a note the model wrote. Soft preferences are low-stakes and fine as notes. A useful rule is that anything with a consequence if wrong gets a record your program controls.

Loading is a decision too. At the start of a session, you could put the student's whole file in the context, or give the model a tool to look it up when needed. The first is simple and cheap for a tiny file. The second keeps the context small when files grow.

Retrieval: finding the right page 6 min

There is a third kind of memory, and it is not about the student. It is the knowledge the assistant needs: hundreds of pages of machine manuals. They are too long for every context and they change rarely, so they live outside the model and are fetched when needed. This is retrieval: searching a collection for the few passages relevant to the current question and putting only those into the context. A common name for the whole pattern is retrieval-augmented generation, or RAG.

An everyday comparison is the index of a textbook. You do not read the book to answer a question; you look up a term, turn to page 212 and read that page.

The steps are:

  1. Chunk. Split each manual into short pieces, such as a section or a few paragraphs. A chunk is the unit that gets stored and returned.
  2. Index. Make the chunks searchable. Keyword search matches the exact words. Embedding search uses an embedding, a list of numbers that places a piece of text so that similar meanings land close together; it can match "how do I stop the blade" with a chunk about an emergency stop. You do not need the maths inside it.
  3. Retrieve. At question time, search with the student's words and return the best few chunks.
  4. Answer. The model reads those chunks in its context and answers from them.
A common mix-up

"Retrieval means the model learns the manual." It does not. Nothing in the model changes. The chunks are text added to one call's context, and they are gone from the next call unless they are retrieved again.

Where retrieval goes wrong

A chunk cut out of a manual can lose its setting. A chunk that says "set the speed to 40" does not say which machine it is for. Anthropic describes this problem and a fix called contextual retrieval: add a short explanation of where the chunk comes from before it is indexed. They report that this cut failed retrievals by 35% with embeddings alone and by 49% when combined with keyword search, in their tests (Introducing Contextual Retrieval). Their numbers come from their own data sets, so measure on your own manuals. The simple version for you: label every chunk with the machine and section it came from.

Retrieval can also be left to the agent. Instead of loading everything ahead, the agent keeps light references such as file names and uses tools to pull data into context only when needed, which the context engineering post calls just-in-time retrieval (Effective context engineering for AI agents). Your search_manuals tool is already this: the model decides when to search and with what words, and it can search again if the first result missed.

Worked example and practice 1 min of reading, then your time

Pulling the pieces together: for each fact, ask three questions. Is it needed on every call? Does it need to survive the session? Is it too big to carry?

Worked example

Where does "the laser cutter is closed for maintenance on Friday" belong?

  1. Needed on every call? No. Only questions about that machine and date need it.
  2. Must survive the session? Yes, and it is the same for all students, so it is shared data, not one student's note.
  3. Too big to carry? No, but it is already in the booking calendar, so the program gets it from check_calendar when asked.
  4. Decision: keep it in the calendar and read it through the tool. Do not copy it into the system prompt, where it would go stale and be paid for on every call.
Your turn

Place these three facts: (a) "never book a machine for a student without current training"; (b) a student's booking history and notes from past visits; (c) the 60-page band saw manual. For each, answer the three questions, starting with (a): needed on every call? Write your decisions down before you open the solution.

Show a solution

(a) Needed on every call: yes, since it is a rule that applies to every booking. It is short, so it goes in the system prompt, which is in the context on each call. The training check itself still happens through a tool, with the record read from the database.

(b) Needed on every call: no. It must survive sessions, so it is saved memory, with the training status as a structured record and preferences as notes. Load it when the student is identified, or let a tool fetch it, so the context stays small.

(c) Needed on every call: no, and it is too big to carry. It goes in a retrieval index, chunked and labelled, and the model reaches it through search_manuals, which returns only the few best chunks.

Summary 3 min

  • The model sees only the context of the current call. Anything that is not sent is invisible to it.
  • Between steps, the program re-sends the growing history, so tokens read grow faster than steps. Trim and shrink tool results.
  • Between sessions nothing survives unless you save it: exact facts as records, soft facts as notes, loaded into later contexts.
  • Big, slow-changing knowledge such as manuals sits in a retrieval index, and only the best chunks enter the context.
