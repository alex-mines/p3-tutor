Context and memory in an agent

By the end of this lesson you can decide, for each piece of information in the makerspace assistant, whether it belongs in the model's context, in saved notes, or in a searchable manual library, and say why.

Why this matters for you

Your assistant must answer from long machine manuals, remember each student's training status between visits, and stay inside a small model budget. All three are context and memory problems. This lesson gives you the vocabulary and the decision rules to defend your design at the review.

Warm-up 2 min

Recall

From memory: in the agent loop, who actually runs a tool, the model or the program? And what does the program do with the result afterwards?

Check your answer

The program runs the tool. The model only writes a request that names the tool and its arguments. The program then hands the result back to the model for the next step. Today's question is what "hands back" means: what the model can see at each step, and what happens to it afterwards.

The context window 5 min

Start with a concrete case. A student types: "Is the laser cutter free tomorrow at 3 pm, and what do I need before I use it?" Before the model writes a single word, the program has to decide what text to send it. A typical request holds:

  • the system prompt: your fixed instructions ("You are the makerspace assistant. Never book a machine without a training record.");
  • the descriptions of the tools (check_calendar, search_manuals, and so on);
  • the student's message.

All of that is text, and the model reads all of it every time it is called. The context is exactly that: everything the model is given for one call. The context window is the limit on how much it can hold, measured in tokens, the small chunks of text (roughly a short word, or part of a longer one) that models read and write. The window covers the input and the model's own output together (Claude context windows documentation).

Two consequences matter for your project.

It limits what fits. If a manual is longer than the window, it cannot be pasted in whole. Even when it fits, a long context is a poor idea: Anthropic's engineers describe context as a finite resource with diminishing returns, and say the goal is the smallest set of high-signal tokens that makes the result you want likely (Effective context engineering for AI agents).

It drives cost. Providers charge by the tokens sent and received. A long system prompt and a pile of unneeded manual text are paid for on every call. With a small sponsor budget, tokens are money.

A rule of thumb: one token is about three-quarters of an English word. Your provider's token counter gives exact numbers; use it before you promise a cost to your sponsor.
Check yourself

Your assistant's system prompt is 2,000 tokens. Over a day it handles 300 requests, each needing three model calls. Roughly how many system-prompt tokens are sent in the day?

Show the answer

1,800,000: 900 calls times 2,000 tokens. Every call is a fresh read of the whole context.

What is kept between steps 6 min

Here is the idea that surprises most newcomers: the model itself remembers nothing between calls. Each call starts blank. What looks like memory inside a conversation is the program re-sending the earlier text every time.

Trace the laser-cutter question through the loop from your last lesson. Each step is a separate model call, and the program builds the next input by appending to the previous one:

Call 1 input:  system prompt + tools + student question
Call 1 output: request check_calendar("laser cutter", "tomorrow")

Call 2 input:  everything in call 1
               + the request for check_calendar
               + the calendar result: "free 1-5 pm"
Call 2 output: request search_manuals("laser cutter training")

Call 3 input:  everything in call 2
               + the request for search_manuals
               + the 3,000-token manual excerpt that came back
Call 3 output: the final answer

This running text is the agent's message history, its working memory. It is kept between steps, and it is the only thing kept between steps; if the program does not send it, the model does not have it (context windows documentation).

That growth is why cost climbs faster than you might expect. If each step adds 1,000 tokens, call 1 reads about 1,000, call 2 about 2,000 and call 3 about 3,000: you pay for 6,000 input tokens, not 3,000. A 20-step run pays for about 210,000.

A common mix-up

"The model remembers the conversation." It is tempting because chatbots feel continuous. But the model is a function from text to text. If the program stops re-sending the earlier turns, the model has no idea they happened. This is also why a bigger window does not give an agent memory across visits: the window is what one call can read, not what survives afterwards.

When the context gets too full 5 min

Since the history grows with every step, a long run eventually hits the window limit, and becomes expensive long before that. The program, not the model, decides what to keep. Three common moves (Anthropic: managing context):

MoveWhat it doesMakerspace example
Clear old tool resultsDrop bulky results that were already used.Replace a 3,000-token manual excerpt with "read the laser cutter safety section".
SummarizeReplace a long history with a short summary, then continue from it."Student wants Friday laser time, passed laser training, no slot booked yet."
Store outside the contextWrite facts to a file or database and read them back when needed.Save the student's training status, covered next.

Every move trades detail for space. Clearing a result the agent needs again forces another tool call. Summarizing can drop a detail that mattered, such as a machine's maximum material thickness. The skill is to keep what the next step needs and drop what it does not.

Anthropic reports that combining context editing with its memory tool improved performance on an internal agentic-search test by 39% over baseline, against 29% for context editing alone (source). Treat the figures as one vendor's benchmark, not a promise for your assistant.

What is kept between sessions: notes 5 min

Clearing and summarizing help inside one run. A different problem: on Monday, Sam completes laser-cutter training. On Thursday, Sam opens a new chat. The context starts empty, so the assistant knows nothing about Sam, and nothing is remembered unless the program saved it somewhere.

Notes (also called long-term memory) are information the agent writes to storage outside the context, such as a file or a database row, so a later session can read it back. Anthropic's memory tool works this way: Claude asks to create, read or update files in a memory directory, and your application carries those operations out against storage you control (memory tool documentation). It is the same loop as before: the model requests, the program acts.

Notes raise design questions you will have to answer:

  • What to save. Facts that stay true and are costly to rediscover: training status, preferred machines, an open booking. Not whole conversations.
  • Who decides. For something as important as training status, do not rely on the model to remember to write it. The program, or the booking system itself, should record it as a fixed step.
  • How to read. Loading every student's notes into every context wastes tokens. Load this student's notes at the start of the session, and no more.
  • Trust and privacy. Notes are about real students. Store only what you need, and make your code refuse any record outside the current student's own; the memory tool documentation says your handler must enforce its storage directory.
A common mix-up

"The assistant will automatically remember students next time." It will not. Unless the program writes notes and reads them at the start of the next session, every visit starts from zero, however capable the model is.

Retrieval: finding the right page 4 min

The manuals are a third kind of memory: reference knowledge that is too big for the context and mostly irrelevant to any one question. A student asking about laser focus does not need the 3D printer chapter. Retrieval means searching a library for the few passages that matter and putting only those into the context for this call.

The usual recipe: split each manual into short passages called chunks, for example one section each; build a search over them, by keywords, by meaning, or both; when a question arrives, search, take the top few chunks and add them to the context. In an agent, search is simply a tool, search_manuals(query), so the model chooses when to look and what to look for. Anthropic describes this as loading data "just in time": keeping lightweight references and pulling in details only when needed, instead of loading everything up front (Effective context engineering).

Retrieval has its own failure modes, worth naming at a design review:

  • Wrong chunk. The search returns the 3D printer page for a laser question; the model then answers from it, or says it cannot find the answer.
  • Chunk too small or too large. A tiny chunk loses the warning that sat one paragraph earlier; a huge chunk wastes tokens.
  • Stale manual. The library holds last year's settings. Retrieval is only as current as what you index.

Keep the manual name and section with each chunk, so the answer can cite where it came from. That also lets a student check a safety-critical claim.

Worked example and practice 3 min

Worked example

Place three items in the design: (1) "Sam passed laser training on Monday"; (2) the policy "bookings may be cancelled up to 2 hours before"; (3) the calendar result for the 3D printer, just fetched for this question.

  1. Item 1 must survive between sessions and is about one student, so it goes in notes, written by the program and loaded for Sam at the start of a session.
  2. Item 2 applies to every student on every call, and is short, so it goes in the system prompt. (If it were a 40-page policy, it would go in the retrieval library.)
  3. Item 3 is needed only for this question and goes stale fast, so it stays in context for now and is cleared once used; the calendar can be fetched again.
Your turn

Place these three: (a) the 60-page vinyl cutter manual; (b) "Priya prefers morning slots"; (c) the rule "never book a machine for a student without a training record". First step: for each one, ask how long it must last and how often it is needed. Then choose context, notes or retrieval.

Show a solution

(a) Retrieval: long reference material, needed only in small parts. (b) Notes: about one person, and must last between sessions. (c) System prompt, as an instruction the model always sees; and because it is safety-critical, also enforce it in the booking code as a fixed check. We return to that choice in the lesson on workflows versus agents.

Summary 2 min

  • The model sees only the context for the current call, limited by the context window and paid for in tokens on every call.
  • Between steps, the only thing kept is the history the program re-sends. It grows, so it must be trimmed: clear, summarize or store elsewhere.
  • Between sessions, nothing survives unless the program writes notes and reads them back.
  • Retrieval finds the few relevant chunks of a large library and puts only those into context, usually through a search tool.

Say it in your own words: without looking, explain to a teammate why Sam's training status will not be remembered next week unless you build something, and say what you would build.
