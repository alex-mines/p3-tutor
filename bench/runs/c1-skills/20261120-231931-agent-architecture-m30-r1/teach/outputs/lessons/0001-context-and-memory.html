Context and memory in an agent

By the end of this lesson you can decide, for each piece of information in the makerspace assistant, whether it belongs in the context window, in a saved note, or in a searchable manual, and justify the choice by its cost.

Why this matters for you

Your mission asks you to decide what the assistant keeps in context, what it saves between sessions, and how it finds the right page in a long manual. Each of those choices also sets the cost per request, which your sponsor's budget limits.

Warm-up 2 min

Recall

From the agent loop: after the model asks for a tool, which part of the system runs the tool, and what happens to the result?

Check your answer

The program around the model runs the tool, not the model. It then sends the result back to the model in the next call. That next call is the subject of this lesson: what exactly goes into it?

Overview: three kinds of memory 3 min

A language model keeps nothing of its own between calls. Everything an agent appears to "remember" is text that the program places in front of the model each time.

That gives three places where information can live, and they differ in lifetime and cost.

  • The context window: the text the model reads in one call.
    • It is the only thing the model can use directly, and every token in it is paid for.
  • Notes kept between sessions: files or database rows that the program saves and reloads.
    • They survive after the conversation ends.
  • A searchable store: a large body of text, such as the machine manuals, that is searched on demand.
    • Only the few passages that match the question enter the context.

The context window 5 min

The context window is all the text the model can take into account when it writes a response, including the response it is writing (Claude documentation: context windows). It is measured in tokens, the pieces of text the model reads and writes, roughly three-quarters of a word each in English.

  • It has a hard limit.
    • If the text for one call would exceed the limit, the call cannot be made as it stands.
  • It has a price.
    • You are billed for the tokens sent in and the tokens written out, on every call.
  • It has a quality limit.
    • Anthropic describes context as a finite resource with an "attention budget": the goal is the smallest set of high-signal tokens that gets the result you want (Anthropic: effective context engineering).

Think of it as the desk you work at while studying for an exam. Everything on the desk is immediately usable, but the desk is finite, and a desk piled with every textbook makes the one page you need harder to find.

What is in the window

  • The system prompt: the standing instructions, such as "You are the makerspace assistant. Never book a machine for an untrained student."
  • The tool descriptions: the names and descriptions of check_calendar, search_manuals and the others.
    • These are text too, so they are sent and paid for on every call.
  • The conversation so far: the student's messages, the model's tool requests and the tool results.
  • Anything else the program adds: saved notes about this student, and retrieved manual passages.

Between steps: the growing transcript 6 min

Between two steps of the same run, the model remembers nothing. The program keeps a list of messages and sends the whole list again on each call. The documentation describes the window as the model's working memory, and later turns add to what is already there (Claude documentation: context windows).

messages = [{"role": "user", "content": question}]
while True:
    reply = call_model(system_prompt, tools, messages)   # reads ALL of messages
    messages.append(reply)                               # keep the model's output
    if reply is final_answer:
        break
    result = run_tool(reply)                             # the program runs it
    messages.append(result)                              # keep the result

Two consequences follow, and both bear on your budget.

  • The context only grows within a run.
    • Step 4 re-reads steps 1 to 3 and is billed for them again.
  • A large tool result is paid for repeatedly.
    • A 30,000-token page dump returned at step 2 is re-sent at steps 3, 4 and 5 as well.

Keeping the transcript small

  • Clear old tool results.
    • Once a result has served its purpose, remove it and keep a short record that the call happened (Anthropic: context management).
  • Summarize.
    • Replace a long stretch of conversation with a short summary and continue from that.
  • Return less from tools.
    • A check_calendar that returns three free slots is cheaper than one that returns the whole month.

Between sessions: notes as memory 5 min

When a session ends, the message list is gone. A student who returns next week starts a new run in which the model has no trace of the last one, unless the program saved something and loads it back.

The standard answer is notes: text saved outside the context window, in a file or database, and read back into the context when needed. Anthropic's memory tool follows this design: Claude stores and retrieves information in a file directory outside the context window, and your application carries out the file operations (Claude documentation: memory tool). The same idea appears in Anthropic's guidance as structured note-taking, where the agent writes notes outside the context and pulls them back in later (Anthropic: effective context engineering).

Everyday analogy: a laundry whiteboard on the fridge. Whoever does the laundry next reads it, so no one needs to remember who washed the towels.

What to write down

  • Durable facts: things that stay true and that the assistant cannot easily re-derive.
    • Example: "Priya completed laser cutter training on 2 March."
  • Preferences and progress: things that make the next session shorter.
    • Example: "Priya is working on an acrylic enclosure."
  • Do not write down: text already stored elsewhere, such as the manuals, or facts that go stale, such as tomorrow's calendar.
    • Stale notes are worse than no notes, because the model will trust them.
Privacy follows from this design. Notes about students are personal data, so decide who can read them and how they are deleted. This is a question to raise at your design review.

Retrieval from long documents 5 min

The machine manuals are too long and too costly to place in every call. Retrieval solves this: the program searches the manuals for the passages most relevant to the question and places only those in the context.

The usual preparation has three parts.

  1. Chunk. Split each manual into passages of a few hundred words, such as one procedure each.
  2. Index. Prepare the chunks for search, either by keywords or by meaning.
  3. Search at question time. Take the top few matching chunks and add them to the context.

Two ways to search

MethodFindsMisses
Keyword searchExact terms, such as a part number "LC-40"Different wording, such as "power" versus "cutting parameters"
Meaning search (embeddings)Passages with similar meaning, whatever the wordingExact identifiers, which it may blur with similar ones

Combining the two is common. Anthropic reports that adding context to each chunk before indexing it, and using both search types, cut the rate of failed retrievals in its tests from 5.7% to 2.9% (Anthropic: contextual retrieval). These figures come from Anthropic's own evaluations, so measure on your own manuals.

There is also a middle path. The agent can be given a search tool and fetch material only when it needs it, rather than loading everything in advance. Anthropic calls this just-in-time retrieval (Anthropic: effective context engineering). In the loop you already know, search_manuals is exactly that tool.

Common mix-ups 2 min

A common mix-up

"A bigger context window removes the need for memory or retrieval." It is tempting because a larger window holds more. But every token in it is billed on every call, and the window still empties when the session ends. A larger window enlarges the desk; it does not add a filing cabinet.

A common mix-up

"The model remembers the conversation." It is tempting because chat feels continuous. In fact the program re-sends the transcript on every call. If the program stops sending a message, the model has lost it.

A common mix-up

"Retrieval means the model searches the manual itself." The search is carried out by the program, in code you write, exactly as with any other tool. The model only requests it, or the program does it before the call.

Worked example and practice 9 min

Worked example: comparing two designs by cost

Request: "Is the laser cutter free tomorrow at 3 pm, and what settings do I use for 3 mm acrylic?" The manual is 60 pages, about 42,000 tokens. The system prompt and tool descriptions total 1,400 tokens, and the question is 50 tokens. All numbers are illustrative.

Design A: put the whole manual in the system prompt. The run has two calls: the first requests the calendar check, and the second reads its result and writes the answer.

  1. Work out the starting context: 1,400 + 42,000 + 50 = 43,450 tokens. The manual is already present, so no search tool is needed.
  2. Call 1 reads 43,450 and requests check_calendar. The request and result add 200 tokens.
  3. Call 2 reads 43,650 and writes the final answer.
  4. Total input: 43,450 + 43,650 = 87,100 tokens.

Design B: retrieve. The run has four calls: the calendar check, the manual search, a training-record check, and then the final answer.

  1. Starting context: 1,400 + 50 = 1,450 tokens. Call 1 reads 1,450 and requests check_calendar; this adds 200.
  2. Call 2 reads 1,650 and requests search_manuals. Request plus three 400-token chunks add 1,400.
  3. Call 3 reads 3,050 and requests check_training_record; this adds 200.
  4. Call 4 reads 3,250 and writes the final answer.
  5. Total input: 1,450 + 1,650 + 3,050 + 3,250 = 9,400 tokens.

Result: Design B reads 9,400 tokens against 87,100 for Design A, about nine times fewer, even though B makes an extra call. The saving comes from not re-sending the manual on every call. Design A also leaves less room in the window, and it cannot grow to ten manuals.

Summary 2 min

  • The context window is everything the model reads in one call; it is limited, billed per token, and rebuilt each call.
  • Between steps, the program keeps and re-sends the transcript, so cost grows with every step and large tool results are paid for repeatedly.
  • Between sessions, nothing persists unless the program saves notes and reloads them.
  • Retrieval keeps long documents outside the window and brings in only the few relevant chunks.
  • Rule of thumb: durable personal facts to notes, changing facts to tools, long fixed reference text to retrieval.
